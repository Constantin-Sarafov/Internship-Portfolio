Overview

THE
IDEA.

Slide & Reveal is a browser-based sliding puzzle generator built as a small gift-giving tool. Instead of just sending a photo, you send a challenge: the recipient has to actually solve a puzzle before they get to see it.

The flow is simple by design. You upload a picture, pick a grid size (which sets the difficulty), and the app spits out a shareable link. Open that link on any phone or PC, and you're dropped straight into a scrambled version of the image — no account, no install, no friction. Solve it, and the full picture snaps into place.

As head programmer on this one, I was also responsible for folding several other standalone mini-games the team had built into a single bundled app in Unity — merging them into one build with a shared menu, consistent navigation, and a common save/settings structure so they could all ship together instead of as separate installs.

Design intent: Zero setup for the solver. If someone has to sign up, install something, or figure out the UI before they can play, the "surprise" of the gift is already ruined.

Heads up: This game was built during an unusually disorganized semester, so if you play it, some things may not work perfectly — expect a few rough edges rather than a fully polished release.

How It Works

UNDER THE
HOOD.

The system breaks into three pieces: the uploader, the puzzle generator, and the shareable link itself.

Uploader. The sender picks an image and a difficulty (easy, medium, hard), which maps to a grid size — for example a 3×3 grid for easy up to a 5×5 grid for hard. The image is cropped to a square and sliced into tiles client-side, so nothing needs to be pre-processed on a server before it can be shared.

Puzzle generator. The tiles are shuffled using a random shuffle that's checked for solvability rather than a pure random sort. Sliding puzzles are only solvable from roughly half of all possible tile arrangements — the rest are mathematically impossible to finish — so the shuffle runs a parity check and re-shuffles if it lands on an unsolvable configuration.

The link. Rather than requiring a database and accounts, the puzzle's state (image reference, grid size, and shuffle seed) is encoded directly into the link. Opening the link regenerates the exact same scrambled puzzle every time, deterministically, from that seed.

Bundling. Since this game shipped alongside several other mini-games in one Unity project, I also handled merging the separate codebases into a single build — resolving overlapping asset names, unifying the menu/navigation layer so all games sat behind one home screen, and standardizing how each game read and wrote save data so they didn't clash. UI and puzzle art assets were designed in Figma and exported straight into Unity's sprite pipeline.

Player Flow

FROM PHOTO
TO PUZZLE.

There are two very different users in this project, and the flow had to work for both of them without a manual:

The sender uploads a photo, drags a difficulty slider, and taps "Generate." That's it — the link is copied automatically, ready to drop into a text or DM.

The solver just opens a link. They land on a shuffled grid with no instructions needed, because the interaction is the same one everyone already knows from physical sliding puzzles: tap or drag a tile next to the empty slot to move it. A move counter and a subtle "getting warmer" cue near the end keep it from feeling like a dead end if someone gets stuck.

On the final correct move, the last tile locks in and the puzzle border does a quick reveal animation before showing the completed image at full size.

Key technique: The solver never sees a loading screen or a "click to start" button — the puzzle is already visible and interactive the instant the link opens, since every second of friction before the "aha" moment works against the whole point of the gift.

Lessons Learned

WHAT I
TOOK AWAY.

01
Going mobile for the first time was the biggest challenge. This was my first project targeting mobile, and the hardest part turned out to be something I hadn't even planned for: getting the image gallery to work. Letting someone pick a photo from their phone's camera roll meant dealing with native gallery/file-picker permissions, handling wildly inconsistent image sizes and EXIF orientation data from phone cameras, and keeping memory usage under control so a full-resolution photo didn't crash the puzzle slicer on lower-end devices.
02
Not every shuffle is a fair shuffle. A naive random shuffle produces unsolvable boards about half the time. Learning the parity rule behind the classic 15-puzzle, and checking for it before ever showing a board to the player, was one of the most important fixes in the whole project.
03
State can live in the URL, not just a database. Encoding the image reference, grid size, and shuffle seed into the link itself meant the app could stay serverless-simple and every puzzle stayed deterministic and shareable without needing accounts or a backend to maintain.
04
Merging separate games into one build is its own skill. Combining multiple mini-games — each built with their own assumptions about navigation and save data — into a single cohesive app taught me a lot about writing integration-friendly code up front, rather than untangling it after the fact.
